# Static trace: hardened M5 Windows Sandbox release wizard

Script: `verification/wizards/wizard-m5-windows-sandbox.sh`

Tracked helper: `verification/wizards/m5-sandbox-checks.ps1`

Run from the repository root with `bash verification/wizards/wizard-m5-windows-sandbox.sh`. The wizard template library above `STAGES` remains identical to the `$wizard` template after line-ending normalization. The generated configuration has exactly two mappings: the prepared kit maps read-only to `C:\M5Kit`, and only its dedicated outbox maps writable to `C:\M5Outbox`. The run pointer, `.wsb`, wizard state, host freshness markers, host acceptance records, and host validation results stay outside both mappings. The configuration explicitly contains `<AudioInput>Enable</AudioInput>`.

## Trust and evidence boundary

The guest may execute only the helper copy in the read-only kit and may write only outbox data. Host validation never invokes a path from the outbox or mapped kit: it invokes the tracked repository helper and pins that helper's SHA-256 on every host action. Before reading any outbox byte, the tracked helper validates its own pinned hash, the host-pinned manifest hash and run ID, all read-only kit artifact hashes, internal FFmpeg/ffprobe wheel-entry hashes, and installer `Zone.Identifier` `ZoneId=3`.

Every guest JSON uses schema `m5-sandbox-evidence-v2` and carries a current `runId`, unique GUID `attemptId`, UTC timestamp, manifest SHA-256, the complete installer/wheel/capture-helper/sandbox-helper/bundled-tool identity set, an evidence kind, an exact kind-specific check-key set, and boolean results. A top-level `pass` is necessary but never sufficient. The tracked host helper parses the JSON, requires every exact check to be boolean true, checks freshness against a host-only attempt marker, and writes a SHA-256 acceptance record under host-only `host-evidence/`. Resume can reuse only an unchanged current-run file with that host acceptance.

Screenshots use exact `<runId>-<kind>.png` names. A host-only freshness marker prevents a pre-existing file from satisfying a new capture, and the tracked helper verifies PNG signature, full System.Drawing decode, minimum legible dimensions of 320×180, run-bound filename, uniqueness across criteria, and SHA-256 before writing a host-only acceptance. The wizard then requires explicit human confirmation that the saved PNG visibly and legibly shows the named UI rather than a blank, unrelated, or duplicate view; the tracked helper persists a separate host-only confirmation bound to run, kind, manifest, helper, and PNG hash. An interruption after decode but before that confirmation cannot resume as PASS. Final validation requires those confirmation bindings and re-decodes and re-hashes all seven distinct screenshots.

## SmartScreen and audio determinism

The staged installer's primary bytes remain hash-identical to the selected release installer while its NTFS `Zone.Identifier` alternate data stream contains `ZoneId=3`. Guest confirmation proves both before launch. Stage 2 requires the expanded SmartScreen reputation UI with `Run anyway` visible; if SmartScreen does not appear despite MOTW, the run records failure. The NSIS installer runs asInvoker and defaults to electron-builder's assisted current-user installation, so UAC is not expected or required. If the installer offers All Users, the wizard keeps the intended current-user/Only for me choice and never selects All Users merely to provoke elevation. Any UAC that Windows happens to show is described only as optional system behavior and cannot satisfy or add to the SmartScreen evidence.

The `.wsb` explicitly enables audio input. Stage 4 requires visible microphone-meter movement with retry/correction instructions. Recording the microphone criterion as failed blocks the mandatory dictated-note run and forces a failed outcome; it cannot silently continue into synthetic or speechless evidence.

## Resume and outcome

Only an incomplete run with an exact parsed `m5-sandbox-kit-v2` manifest identity resumes. Any existing dated outcome starts a new run. Guest retries use unique attempt IDs and never replace raw evidence; host acceptance records may be replaced only after a fresh strict acceptance. Wizard state is host-only. A PASS outcome requires every listed human observation, the SmartScreen screenshot and six other current-run screenshots, all three strict guest evidence acceptances, microphone movement, and trusted final validation. UAC and elevation are not PASS criteria. A recorded FAIL uses the red failure frame and leaves M5 in `PLAN.md`; the wizard does not perform or claim the human run.
